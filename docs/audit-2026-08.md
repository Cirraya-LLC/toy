# One round of adversarial audit before toy shipped: 33 findings, 16 confirmed, 17 overturned

*August 2026 · before the toy v0.1.0 release*

toy is a tool for installing binaries, and its only selling point is that
**not one line of script runs while it installs anything**.
A tool that sells "does not execute" has to prove it does not execute — so before we cut
the first tag, we ran an adversarial audit across the whole codebase.

This is what that round looked like and what came out of it, including **a critical we
found in our own design**: Iron Law 1 fully bypassed, and bypassed cleanly.

---

## 1. Method

The audit had three stages, deliberately kept from talking to each other.

### Stage one: eight attack surfaces, working in parallel

Work was split by **what an attacker wants**, not by package. Eight surfaces read the same
code independently:

| Surface | The question it asked |
| --- | --- |
| Execution | Is there any path at all by which code inside a package gets run? |
| Hashing | In what situations is "we verified it" a lie? |
| Paths | What can be written somewhere it should not be? |
| Extraction | What can be stuffed into a tar or a zip? |
| Terminal injection | Can the line printed for the user be rewritten? |
| Signatures | What does `✓ signed` actually prove? |
| Network | Can the transport be downgraded, redirected, or blown up? |
| Robustness | Which failure leaves the user worse off than not installing at all? |

Splitting by surface rather than by package matters because **the expensive bugs cross
package boundaries**. The critical from this round is exactly that: half of it lives in
`internal/store` (creating the symlink), half in `internal/host` (running git). Neither
package looks wrong on its own — because neither one is.

### Stage two: falsify every finding from three angles

Once the thirty-three findings existed, **they did not go to be fixed. They went to be
refuted.** Three independent angles each argued that a finding was unreachable:

- **Reachability**: starting from a real entry point, does this path actually get there?
- **Preconditions**: do the conditions it needs hold, or does it require the attacker to
  already have a stronger capability?
- **Semantics**: is this a bug, or is it the behavior the user explicitly asked for?

A finding had to survive all three to live. **17 were overturned — more than were confirmed.**

That ratio is the point. A round where everything is confirmed usually means the bar was
too low, and every "hmm, that looks off" got written down as a finding.

### Stage three: fix the confirmed ones, grouped by package

The 16 confirmed findings were grouped by package and fixed one package at a time. The
cross-package one (the critical) was handled separately.

## 2. The main course: a package can get execution, and Iron Law 1 still holds literally

### The attack

A `toy.toml` says:

```toml
[bin]
git = "payload"
```

After installing, `~/.toy/bin/git` is on PATH.

And `~/.toy/bin` is exactly the directory `toy doctor` tells the user to put **first** on
PATH — it has to be first, or the tools you install get covered by same-named programs
already on the system.

**toy discovers versions by running `git ls-remote`.** That is a deliberate design choice:
no GitHub/GitLab REST API, because 60 unauthenticated requests per hour would wall users
off on day one and it would mean writing three adapters. One `git ls-remote` command
behaves identically across every git host.

So: the next `toy install github:…`, `toy update`, `toy publish`, or `toy doctor` runs a
file out of that package.

**Not one line ran at install time.** Iron Law 1 holds literally. Execution was merely
**deferred by one command**.

### Why the shadowing check does not catch it

Iron Law 5 is "never shadow a command already on PATH, unless `--force`". It exists for
exactly the `bin = "sudo"` family of attacks. It looks like `bin = "git"` should be caught
by the same check.

It is not — because that check's test is whether `exec.LookPath("git")` **finds anything**.

On a machine **that does not have git yet**, `LookPath` finds nothing, so it is not
shadowing, so the check waves it through.

And "a machine without git" is not a contrived precondition:

- macOS without Xcode Command Line Tools — that is a brand-new Mac, where `git` is a stub
  that pops up an install dialog.
- Slim container images, CI base images — installing git is an explicit line you add.
- **And toy's bare-URL install route (`toy install https://…/toy.toml`) does not need git
  at all.**

That last one makes the whole precondition self-consistent: the attacker does not need the
victim to have git installed. He needs the victim to install one thing by bare URL — which
is precisely toy's most prerequisite-free install route.

The first toy package installed on that machine can be this package.

### The fix is in two halves, and neither one works alone

**First half, `reservedLinkNames` in `internal/store`**: refuse to link any package as `git`.

```go
// reservedLinkNames are the programs toy itself execs from PATH BY NAME.
var reservedLinkNames = map[string]bool{"git": true}
```

This is the **only check in the entire project that `--force` does not waive**.

The reason is not "more dangerous, therefore stricter". It is that **the user cannot reason
about the consequence**. The `bin = "sudo"` prompt says "sudo is already on your PATH; add
`--force` if you really mean to override it", and the user understands that: he knows what
sudo is and what overriding it means. But "this package would like to be called git" reads
to a user like a coincidence — nothing tells him that agreeing hands over toy's own next
execution.

Nor does any package have a legitimate reason to claim a name from toy's own toolchain.
There is no legitimate use case here that needs unlocking, so this door should not have a key.

**Second half, `lookupGit()` in `internal/host`**: walk PATH ourselves, resolve an absolute
path, **skip `$TOY_HOME/bin`**, and skip relative PATH entries (`.` and that empty entry
that is everywhere — running toy inside a directory somebody else can write to should not
mean handing over Iron Law 1).

When the fake git is the only git on PATH, we do not vaguely report "git not found". We say:

> Refusing to run — the only git on PATH is `~/.toy/bin/git`, which lives in toy's own bin
> directory, meaning it came from an installed package. toy discovers versions with
> `git ls-remote`, so running it would hand that package execution — **this is most likely
> an attack.**

**Why both halves are needed:** the first half only stops newly installed packages — it does
nothing for a machine that is already compromised. The second half refuses to run a git
already sitting in `bin/` — but it does not stop that symlink from being created, and a
fake git that can be created will still fire in other contexts (the user typing `git` himself).

### Two pieces of debt left behind

`internal/host` may not import `internal/store` (import cycle), so the bin-directory
derivation exists in both places, with comments pointing at each other. **Change one and
forget the other and this defense fails silently, and failing looks exactly like working.**

And the moment toy execs one more external program **by name**, that name has to be added
to `reservedLinkNames`. Right now that rule is remembered only by a comment and by this
article — nothing automated will remind whoever adds the second `exec.Command`.

Reproductions in `cmd/toy/ironlaw1_audit_test.go`, `internal/store/link_audit_test.go`,
and `internal/host/exec_audit_test.go`.

## 3. A few of the others

### Change one `source` line in an index and you replace the contents of an installed package

An index entry is only a **pointer at a repo** — a deliberate design choice, because it
means deleting an entry only makes a package unsearchable: `github:owner/repo` still
installs it, and nobody can actually kill a package.

The price is that `toy update` re-resolves through the index entry. Change `source` from
`alice/tool` to `evil/tool` and the contents of the command on the user's PATH become
something from a different repo — **with not one gate in the way**:

- The trust-downgrade check only catches `signed → not signed`. When neither side is
  signed, it does nothing.
- The TOFU record's id is `<host>:<owner>/<repo>@<tag>`. Swap the source and it is a
  **brand-new record**, so it is judged a first install: no warning, straight to pinned.

Same root, second finding: **the author's public key is pinned against that same
source-derived id**, so changing the source changes identity, and the key that was pinned
does not apply to the new id.

The fix makes "the source changed" something that has to be declared: stop by default,
`--force` lets it through, but **a waiver has to print which repo it switched to**.

### `search --json` reported "there is a key in the index" as `signed: true`

Without verifying a single signature.

This one is worth recording because it is **the same bug appearing a second time**. The
first time was found during integration: `index.Entry` did not even have a `sig` field
then, and the parse path printed `✓ signed` on the mere sight of a `key` — while an index
is a JSON file anyone can fork and anyone can send a PR against, and copying a public key
costs nothing. That fix covered the human-facing path.

`--json` is a second path, and it got missed. **A security decision with two exits is not
fixed when you fix one.**

### The trust column in `toy list` can be pushed off the screen by a package name

This one needs no control characters at all.

`toy list` lays out its table with tabwriter, and column width is the widest cell plus two.
`name` comes straight from `toy.toml`, and validation only rejects control characters and
path separators — **no length cap, and no opinion about runs of spaces**.

So a package can write its `name` as a whole forged table row:

```
cowsay    v3.2.1  ✓ signed 9f3c1a20  Derrity/cowsay
```

padded with spaces past the terminal width. On any terminal narrower than that name:

- The package renders as the line above — a signed cowsay.
- Its real `⚠ unsigned` is pushed past the wrap (`toy list | less -S`, or tmux, just cut it off).
- **And it takes the trust column of every legitimate package in the same table, jq
  included, off the screen with it.**

Iron Law 8 says the trust level must be printed honestly. This attack does not make it lie
— it makes it **invisible**, and invisible is harder to notice than a lie.

The fix has three layers: cap every cell by rune count; lay the table out in memory and then
run every line through the escaping layer; and **put the trust column first** — nothing can
push the first column off the right edge.

The same surface had a subtler one: the escaping function claimed to cover the C1 control
characters (0x80–0x9f), but **a raw `0x9b` byte went straight through** — the fast path
scans with `strings.IndexFunc`, which decodes invalid UTF-8 as U+FFFD (not a control
character), so the whole string was judged clean and returned as-is. `0x9b` is the 8-bit
form of CSI, and on a terminal interpreting 8-bit C1, `CSI 1A` + `CSI 2K` is cursor-up one
line plus erase the line — exactly enough to overwrite the trust level printed above.

Meanwhile the same code point written as valid UTF-8 (`0xC2 0x9B`) was escaped correctly.
**Same byte, and the outcome depended on whether some other part of the string happened to
contain a control character. A sanitizer that works by luck is not a sanitizer.**

### The one that belongs to `net/http`

toy echoes URLs back in error messages. A user may have put credentials in the address
(`https://u:p@host/…`), so the password gets stripped when the error is built.

That was done — but one exit was missed: **when `CheckRedirect` returns an error,
`net/http` puts the original `Location` back into `url.Error.URL`**, and that path does not
go through our stripping function.

Consequence: an upstream that redirects you to `https://user:pass@…` can use the standard
library to carry credentials into the error object. And error objects go into logs, into
issues, into `--json`.

The fix strips them in place inside `fetch.open()` rather than relying on the output layer
— the output layer is a backstop, not a fix.

Two more the network surface confirmed in the same round: **https silently downgraded when
redirected to http** (the test has to scan the whole via chain; comparing only the last hop
misses the middle hop of `http→https→http`), and **downloads with no size ceiling** (the
measure has to be bytes actually written, not `Content-Length` — a server-reported length
is untrustworthy, and chunked transfers do not report one at all).

### `--force` was one switch waiving six things

Three independent angles ran into the same problem.

`--force` used to waive all at once: reinstalling the same version, the artifact hash
changing, the author's public key changing, a command-name shadow, a trust-level downgrade,
and the source changing.

**A user who wants to reinstall once was thereby accepting the other five — which is the
entire reason TOFU exists.**

Split in two:

- `--reinstall`: means only "I know this version is installed, install it again".
  **Everyday operation, touches no safety check.**
- `--force`: accepts the changes a safety check reported, **and prints what it waived, one
  line each**.

That second sentence is the important half. A silent waiver is the same as not having the check.

## 4. The 17 that were overturned

This is the section that shows the process was not theater.

The reasons fall into three groups.

### "Plausible, but unreachable"

**Write `file:///etc/shadow` as an `[artifact]` value, and toy reads an arbitrary local
file, installs it into PATH as a binary, and helpfully caches it into `~/.toy/cache` —
which is the directory `toy serve` hands out.**

This held when it was raised. But another fix from the same round — `toyfile` rejecting
`artifact`/`script` values that are absolute URLs with a scheme — closed it in passing: the
address can only be assembled by toy from the host template.

**git's `ext::` transport can execute arbitrary commands** (`ext::sh -c 'touch /tmp/PWNED'`
as a repo address). Two independent reasons make it unreachable: git has disabled the ext
transport by default since 2.12; and more importantly the clone address's prefix comes from
the host table (the four built in, or the user's own config), with owner/repo constrained to
`[A-Za-z0-9._-]` (not even a colon allowed) — **what a package author controls is
`toy.toml`, and nothing in `toy.toml` can reach the clone address.**

**A cross-host redirect carrying `Authorization` to a second machine.** `net/http`'s
`makeHeadersCopier` drops sensitive headers on a host change, including the one derived
from URL userinfo.

**A redirect to `file://` to read local files.** The Transport has no file protocol
registered.

### "Already defended, just never written down"

This group **gains value by being overturned**, because each one names an optimization that
looks safe to make.

**Cache hits do not re-hash** (checking only that a file named after the declared hash
exists, so anyone with filesystem access can plant a file with the right name and the wrong
content). Review: not true, that re-hash is already in the code.

But that re-hash **looks exactly like a disk read you could skip** — and skipping it turns
`~/.toy/cache` into a trust root anyone can write to, in a directory that is also the mirror
source `toy serve` publishes.

**A failed download leaves a half-written temp file**: not true, one flag covers every
failure path. But the day somebody adds one more `return` and forgets it, the cache
directory starts growing half-files.

**Mirrors are tried even without a sha256**: not true, there is an early return. The entire
premise for mirrors "not needing to be trusted" is that content can be checked against a
hash — with no hash the premise fails, so that fallback path has to **disappear entirely**
rather than degrade into being used anyway.

**sha256 handling of case / whitespace / an `0x` prefix**: correct in both directions. The
line it holds is "liberal in, strict out": case and whitespace are ordinary noise from an
author hand-copying a `toy.toml` and must be tolerated; length and character set must not be,
because that string gets used as a filename in the cache and as a path segment in a mirror URL.

The extraction surface overturned a batch of its own: setuid/setgid bits do not survive; hard
links cannot point at system files; zip backslashes and a directory entry with the same name;
path traversal in a PAX extended header; the same member appearing twice; overlong paths;
whether chmod after umask could widen permissions; whether the cleanup logic could delete
outside the destination. **All of these were flipped into regression tests**, see the next
section.

### "That is not a bug, that is what the user asked for"

**`toy install foo@v1.0.0` installed a version older than the v2.0.0 already installed.**

Overturned: the user **explicitly asked for it**. Blocking it would only make "I want to go
back one version" impossible.

But overturning it grew a real finding right next door: **upstream deleting the newest tag**
(account taken over, release pulled, a self-hosted host swapped out) travels **the same path**
— and in that case the output said only "installed t 1.0.0", with not one word about a
downgrade.

So it still installs, but **it has to say so**.

This was the most interesting overturn of the round: the act of falsifying a finding squeezed
out the real problem. Had we treated it as a bug and fixed it directly (refuse downgrades),
we would have gotten a more annoying tool **and the real problem would have stayed exactly
where it was.**

## 5. Closing: the tests from the overturned findings were not deleted

Every finding got a reproduction test before it was falsified — asserting "this attack should
succeed".

For the 17 that were overturned, those tests were **not deleted. They were flipped into
regression tests**: the assertion changed from "should succeed" to "must be refused". The top
of each file states three things:

1. What was suspected
2. Why it does not hold
3. What is being held down now

One example:

```go
// Regression (Iron Law 4): a cache hit MUST re-hash, not just check that the file is there.
//
// Suspected: the cache decides a hit by filename alone (= the declared hash), so anyone with
// filesystem access could plant a file with the right name and the wrong content and have it
// installed directly.
// Review verdict: does not hold — the SumFile call in Get already re-hashes. This is not a
// fix, it PINS that re-hash: it looks like a disk read you could skip, and skipping it turns
// ~/.toy/cache into a trust root anyone can write to (and that directory is also toy serve's
// mirror source).
```

The reasoning is simple: **what overturned a finding was this version of the code.** The next
refactor may take that reason away — and nobody will remember that somebody once suspected
this spot.

Those tests now live in `*_audit_test.go` alongside the ones for confirmed fixes. Their value
is not "proof that we audited". It is **turning one act of human reasoning into an assertion a
machine re-checks every time.**

## Appendix: the constraints this round settled

A few things that must not be broken, all of them grown out of this round:

- Names in `reservedLinkNames` are not waived by `--force`; adding one `exec.Command` means
  adding one line here.
- `--force` and `--reinstall` are two different things; do not put a new waiver back into
  `--force` without printing it.
- **Never print the repo owner** after `✓ signed`. The signed message is
  `id + source + the raw toy.toml`, all three publicly readable, and **not one byte of them
  binds the key to the owner**. Details in `SECURITY.md`.
- Everything printed for a human goes through the escaping layer; tables are laid out in
  memory and then emitted line by line.
- Credentials are stripped at the moment the error is constructed, never left to the output
  layer.
- TOFU pins by asset name, not by `ref@version` — otherwise a musl machine and a glibc
  machine sharing a `$HOME` report "the content was swapped out" at each other, a false alarm
  in the one place you can least afford to cry wolf.
